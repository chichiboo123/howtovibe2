03

왜 Supabase인가

강사의 솔직한 경험담

▼

화면이 스프레드시트처럼 생겨서 설명이 거의 필요 없고, 여러 명이 동시에 써도 버티며, 실시간 기능이 준비되어 있습니다. 무엇보다 로그인을 붙이지 않아도 잘 돌아갑니다.

실제로 겪은 일

Apps Script와 스프레드시트로 질문 공유 앱을 만들어 본 적이 있습니다. 혼자 쓸 땐 훌륭했는데, 한 반이 동시에 접속하니 느려지고 가끔 글이 겹쳐 쓰였습니다.

emoji_objects 결론 더 좋은 기술이라서가 아니라, 이 용도에 맞아서입니다. 한 명씩 순서대로 쓰고 교사만 확인하는 앱이라면 Apps Script가 오히려 편합니다.

표를 만들고 문지기를 세웁니다

20분 ▼

terminal 테이블 만들기

직접 칸을 만들지 않습니다. 아래 SQL을 Supabase의 SQL Editor에 붙여넣고 실행하세요. 칸 종류를 하나씩 고르다 보면 시간이 다 갑니다.

-- 감정 체크인 테이블
create table checkins (
  id         bigint generated always as identity primary key,
  room_code  text not null,   -- 수업 코드 (예: today-5-3)
  emotion    text not null,   -- 감정 (기쁨/평온/걱정/피곤 ...)
  note       text,            -- 한 줄 메모 (선택)
  created_at timestamptz default now()
);

-- 문지기(RLS) 켜기
alter table checkins enable row level security;

-- 읽기 허용
create policy "read_all"   on checkins for select using (true);
-- 쓰기 허용
create policy "insert_all" on checkins for insert with check (true);

-- 수정·삭제 정책은 일부러 만들지 않습니다.
-- 정책이 없으면 막히는 것이 기본값이라, 학생은 남의 글을 지울 수 없습니다.
-- 삭제가 필요하면 Supabase 대시보드에서 교사가 직접 처리합니다.

이 코드가 하는 일은 세 가지입니다. 표를 하나 만들고, 문지기를 세우고, "읽기와 쓰기만 허용한다"고 알려주는 것.

안전한 설계 3원칙

원칙 1

적게 받으면 지킬 것도 줄어든다

이름·학번·이메일·계정 대신 수업 코드 + 익명. 별명을 쓴다면 "실명 대신 별명을 사용하세요"를 화면에 안내합니다.

원칙 2

공개 키를 숨기는 게 보안이 아니다

브라우저용 공개 키는 클라이언트 코드에 포함될 수 있습니다. 핵심은 RLS와 권한 설정으로 데이터 접근을 제한하는 것입니다.

원칙 3

지울 수 있어야 한다

언제 어떻게 지울지를 처음부터 정합니다. 수업이 끝나면 남길 이유가 없는 데이터는 남기지 않습니다.

출석번호에 대해 출석번호도 학급 안에서 특정 학생을 식별할 수 있는 경우 개인정보에 해당할 수 있습니다. 그래서 오늘 실습에서는 쓰지 않습니다. 꼭 필요한 앱이라면 무엇을 위해 필요한지 먼저 따져보세요.
개인정보를 안 받아도 끝이 아닙니다 개인정보 처리 부담은 낮아지지만, 학생이 작성한 내용의 공개 범위와 접근 권한은 별도로 보호해야 합니다. 익명이라도 감정이나 고민을 쓴 글은 함부로 노출되면 안 되고, 부적절한 글이 올라올 가능성도 함께 생각해야 합니다.

          브라우저에 무작위 번호를 심는 방법도 있지만, 그 값은 얼마든지 흉내 낼 수 있어서
          실제 보호 장치가 되지 못합니다.

        
제대로 하려면 Supabase의 익명 인증을 씁니다.
          학생에게는 회원가입·로그인·이메일 입력 화면이 전혀 나타나지 않지만,
          내부적으로는 앱이 사용자를 구분합니다.

        

          

-- 사용자 구분 칸을 추가하고, 본인 글만 고칠 수 있게 합니다
alter table checkins add column user_id uuid default auth.uid();

create policy "update_own" on checkins for update
  using (auth.uid() = user_id);

create policy "delete_own" on checkins for delete
  using (auth.uid() = user_id);

        

        

          
동작 순서

          
학생 접속 → 익명 인증 자동 실행 → 사용자 식별값 생성 →
            글 저장 시 그 값이 함께 저장 → 자기 값과 일치하는 글만 수정·삭제

help교사가 직접 만든 앱도 대상인가요?

          
심의 대상 요건에 해당하면 대상이 됩니다. 다만 교육부 심의 가이드에는
            교사가 개발자인 경우 교사가 판단하고 증빙할 수 있으며,
            증빙은 개인정보 처리방침으로 갈음하거나 기준 세부 내용에 대한
            서술형 답변으로 대체할 수 있다고 안내되어 있습니다.

        
help학운위 위원들이 소프트웨어를 잘 모르는데요?

          
소프트웨어 내용을 일일이 검토하는 것이 아니라, 체크리스트가 충족으로 표기되어 있는지와
            증빙자료가 갖춰졌는지를 확인하는 방식으로 안내되어 있습니다.

        
help서면 심의도 되나요?

          
원칙적으로 대면이 바람직하며, 불가피한 경우에 한해 허용될 수 있다고 안내되어 있습니다.

        
help한 차시만 잠깐 써도 심의해야 하나요?

          
사용 기간과 무관하게 정규 교과 수업에 활용되고 요건에 해당하면 심의를 거치도록 안내되어 있습니다.

        
help여러 개를 쓰면 하나씩 다 심의하나요?

          
기업 단위가 아니라 소프트웨어 단위입니다. 다만 일괄 상정 간소화 절차가 있습니다.
